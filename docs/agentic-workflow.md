# Agentic Workflow — 스킬 실행 사양

스킬 호출 → 입력 수집·검증(Phase 0) → 4단계 agentic workflow.
화이트보드 설계를 옮기고, 아래 4대 목적 기준으로 불확실 지점을 확정한 문서.

## 북극성 — 이걸 왜 하는가

모든 단계·모든 Validator의 판단 기준은 이 넷이다.

| # | 원칙 | 의미 |
| --- | --- | --- |
| P1 | **AI가 만든 티가 나지 않는다** | 최종 페이지는 디자이너 완성본과 구분 불가해야 함. 비평자(reviewer)의 제1 기준 |
| P2 | **정해진 템플릿을 최대한 활용한다** | 커스텀 레이아웃은 템플릿이 정말 안 맞을 때의 예외. 기본은 [layout-catalog](analysis/layout-catalog.md) |
| P3 | **주어진 asset을 최대한 활용한다** | 사용자가 준 asset(T2 포함)이 1순위. 생성은 주어진 것으로 부족할 때만 |
| P4 | **Image Generation을 이용한다 (Higgsfield)** | 부족한 부품은 Higgsfield MCP로 생성 (T1). 단, P1·컴플라이언스 게이트를 통과해야 함 |

> P3 → P4 순서가 곧 우선순위다: **주어진 것 먼저, 생성은 그다음.**
> asset 3계층([assets.md](assets.md))과의 대응 — T0 절차생성 / T1 AI생성(=P4) / T2 주입필수(=P3, 생성하면 위조).

전체 구조:

```
[Skill 실행]
     ↓
  Phase 0 — Input 수집·검증  (게이트 통과까지 반복)
     ↓
  1단계 Design System → 2단계 Layout 설계 → 3단계 부품 준비 → 4단계 조립
```

---

## Phase 0 — Input 단계

스킬이 호출되면 **바로 작업을 시작하지 않는다.** 필요한 입력을 순서대로 요구하고,
각 입력마다 `Validated?` 게이트를 통과해야 다음으로 넘어간다.

### ① 기획서

```
"기획서를 주세요" → 기획서 제공 → 읽을 수 있으면 → ✅ Validated
```

- 요구: 기획안 파일(xlsx)
- 검증: 파싱해서 장면·카피를 읽어낼 수 있는가 (`parse_brief.py` 기준)
- 실패 시: 무엇이 안 읽히는지 말하고 다시 요청

### ② 필수 사용 asset (P3)

```
"이 기획서에서 특별히 사용해야 하는 asset이 있는가?"
     → 경로 조회 → Validation → ✅ Validated
```

검증 항목:

1. **경로 실재** — 폴더 위치·파일명이 맞고 접근 가능한가 (+ 용량 확인)
2. **용도 명시** — 각 asset이 아래 중 무엇인지 선언되어 있는가

| 용도 | 의미 | 계층 |
| --- | --- | --- |
| 배경용 | 페이지 배경/질감으로 직접 깔림 | T2 주입 |
| 참조용 | 스타일·형태 참조만, 직접 배치 안 함 | reference |

> 두 용도가 섞인 채 들어오면 반려. 배경용/참조용이 나뉘어야 Validated.
> 용도가 없는 asset은 사용자에게 되물어 확정한다 — 추측으로 배치하지 않는다 (P3의 전제는 "의도대로" 활용).

### ③ 추가 지침

```
"추가 advise / 꼭 유념해야 할 사항은?" → 입력 → 모호한 부분 되묻기 → 확정 → ✅ Validated
```

- 자유 서술 입력. 해석이 갈리는 지점은 반드시 되물어 확정
- 확정된 내용은 이후 모든 단계의 제약조건으로 전달

**세 게이트를 모두 통과해야** 1단계가 시작된다.

---

## 1단계 — Design System 확정

```
기획 전체 view → font/color 기준 수립 → [HITL] 조정 루프 → approve → 2단계
```

- 개별 페이지가 아니라 **기획 전체를 조망**한 뒤 토큰을 정한다
- 산출물: font / color / **surface(배경 표면 시스템)** 체계 (기존 [design-tokens](analysis/design-tokens.md) 위에서 선택·조정)
- surface = solid/texture/gradient/photo 4어휘의 **비율 선언**. 톤앤매너의 함수로 여기서 정하며,
  블록별 즉흥 결정 금지. 단색 과다(>60%)는 다양성·창의성 부족 (craft-axioms §3.1)
- **HITL**: 사람이 보고 조정 요청 → 반영 → 재확인, `approve` 전에는 2단계 진입 금지

---

## 2단계 — 페이지 단위 Layout 설계

각 기획 페이지(장면)별로 결정한다.

### 2-1. 레이아웃 선택 (P2)

- 각 페이지에 **layout-catalog의 어떤 템플릿을 쓸지** 결정 — 템플릿 우선이 원칙
- 커스텀 레이아웃은 **템플릿 중 정말 맞는 게 없을 때만** 설계하고, 왜 템플릿이 안 되는지 사유를 남긴다

### 2-2. 컴포넌트 슬롯에 asset 배치 (P3 → P4)

레이아웃의 각 컴포넌트 자리에 무엇이 들어갈지 확정:

```
asset ┬ 누끼 (제품컷)
      └ 배경 ┬ 사진
             └ 절차적 텍스처 (T0)
```

- **주어진 asset부터 소진** (P3) → 그래도 비는 슬롯만 **AI 생성 대상으로 표시** (P4)
- "AI 생성해야 하는 부분이 어디인지"를 이 단계에서 **목록으로 확정**한다 → 3단계의 작업지시서
- 각 페이지에 어떤 font/color를 쓸지도 여기서 1단계 체계 안에서 배정

### 2-3. 검증

- 2단계 산출물(레이아웃 플랜)을 **Rule set = [craft-axioms](analysis/craft-axioms.md) + [rules.md](rules.md) + compliance** 에 대조해 Validate
  - asset이 선언된 용도대로 쓰였는가 (배경용이 배경에, 참조용은 직접 배치 안 됨)
  - 템플릿 이탈(커스텀)에 사유가 있는가 (P2)
  - AI 생성 목록에 T2(증거성) asset이 들어있지 않은가 — 있으면 즉시 반려 (위조 금지)

---

## 3단계 — 사전작업: Component 재료 준비 (P4)

조립 전에 **부품을 먼저 다 만들어 놓는다.**

```
2-2에서 확정된 생성 목록
     ↓
Higgsfield로 생성 (AI 이미지 / 누끼 가공 / ...)
     ↓
[Validator] ⟲  불합격 → 재생성 요청 (루프)
     ↓ 합격
[HITL] ✓  사람이 최종 확인
```

- 생성 provider는 **Higgsfield MCP** (P4, 사용자 확정 결정 — Gemini/FLUX는 fallback)
- Validator 기준: P1(AI 티 — 손가락·텍스트 뭉개짐·비현실 질감 등) + 컴플라이언스 게이트
- 루프를 돌아도 기준 미달이면 사람에게 에스컬레이션, 통과분도 HITL로 최종 승인

---

## 4단계 — 조립

```
1~3단계에서 잡은 전략 그대로 조립 (여기서 새로 창작하지 않는다)
     ↓
[Validator] — 설계대로 조립되었는가 + craft 채점
     ↓
Feedback loop: 기준(80점 + 실격 0건)에 맞을 때까지 반복
```

- 4단계는 **실행 단계**다. 전략·배치·부품은 이미 확정돼 있고, 여기선 그대로 짓기만 한다
- **생성자/비평자 구도 (GAN 유사)**: 빌더가 조립 → `detail-page-reviewer` 에이전트가 렌더 이미지를 보고 craft-axioms로 채점·지적 → 빌더가 수정 → 반복
  - 이미 검증된 구조: 기존 4-layer 판정 스택 (compliance > craft > deterministic checker > reviewer). v2가 6라운드에 84점, v3가 1라운드에 83점 통과
  - 비평자의 제1 렌즈는 P1 — "AI가 만든 티가 나는가"
- **룰을 약화시켜 통과시키는 것 금지** (기존 원칙 유지)

## 런(run)의 경계 — 입력 독립성 원칙 (2026-08-17 신설)

이 파이프라인의 목표는 **다양한 입력에 잘 동작하는 것**이다. 구스밀은 테스트 입력일 뿐이다.
v7 사건(같은 세션에서 v6 디자인 시스템을 무단 승계)에서 도출된 규칙:

**상태의 2계층:**

| 계층 | 내용 | 위치 |
|---|---|---|
| **시스템 상태** | 규칙·공리·체커·템플릿·레시피 — 모든 입력에 공통 | docs/, pipeline/, .claude/ |
| **실행 상태** | 이 입력의 플랜·판정·에셋·사실 | `data/briefs/<product>.*`, `data/assets/<product>/` |

**참조 규칙:**

1. **새 입력의 실행은 시스템 상태만 참조한다.** 타 제품의 plan.json·판정 이력 참조 금지
2. **같은 제품의 재실행**이 승계할 수 있는 것: compliance 판정·확정 수치·T2 에셋.
   승계할 수 없는 것: **디자인 시스템(팔레트·표면·세계관) — 매 실행 §4로 재도출**
   (사용자가 명시 제공한 경우만 예외)
3. **제품의 사실은 plan.json이 소유한다.** 체커·스킬에 제품 사실을 하드코딩하는 것은
   오염이다 (실례: qa_check의 `NUM_NEAR`에 "갈비살 함량"이 박혀 있었다 → `fact_checks`로 이사)
4. **이관 기준**: 검수 루프에서 체커로 내리는 것은 **일반화 가능한 규칙만**.
   "이 제품에서 이 수치가 충돌했다"는 사실은 plan으로, "수치 충돌을 검사하라"는 규칙만 체커로
5. 문서의 제품 사례 인용(공리의 근거 노드 등)은 정당하다 — 단 **사례는 규칙이 아니다**를
   문서가 명시한다

**독립성 테스트 프로토콜 (구현됨, 실행은 별도 지시):**
- 테스트 A: 새 세션 + 다른 카테고리 기획안 → 산출물이 기존 산출물과 구별되는가
- 테스트 B: 새 세션 + 같은 기획안 → 팔레트(패키지 파생)는 유사하되 세계관·표면·모티프가 달라지는가
- 판정: 디자인 시스템 도출이 §4를 실제로 탔는가 (플랜의 note에 도출 근거 필수)

## 관통하는 원칙

1. **Validate 없이는 다음 단계 없다.** 입력·설계·부품·조립 각각에 게이트가 있다.
2. **HITL은 1단계(디자인 시스템 approve)와 3단계(부품 승인)에 명시적으로 존재한다.**
3. **전략은 앞에서, 실행은 뒤에서.** 4단계에서 즉흥 결정이 나오면 그건 2단계의 실패다.
4. **asset은 용도·계층으로 분류된 채로만 흐른다.** 배경/참조 × T0/T1/T2 — 섞이면 반려.
5. **Validator는 하나의 판정 스택, 단계별로 적용 룰만 다르다.**
   (Phase 0: 입력 무결성 / 2단계: 플랜 vs Rule set / 3단계: 부품 품질·P1 / 4단계: 조립 vs 설계 + craft 채점)

## 화이트보드 대비 확정한 해석

원본 손글씨에서 불확실했던 지점을 4대 원칙 기준으로 확정한 기록:

| 지점 | 확정 | 근거 |
| --- | --- | --- |
| Phase 0 ② 취소선 항목 | 폐기 — "필요한가/잘 연결되나"는 경로·용도 검증에 흡수 | 남은 두 검증 항목이 상위 호환 |
| 배경 asset의 "영상" | **범위 밖** — 산출물이 정적 Figma 상세페이지 | 스코프(Level 1/2) 정의 |
| "Rule set" | 새 개념 아님 — 기존 craft-axioms + rules.md + compliance | P2, 기존 판정 스택 재사용 |
| Loop engineering / GAN | 기존 빌더 ↔ reviewer 루프의 다른 이름 | 이미 v2/v3에서 검증된 구조 |
| Validator 개수 | 단일 판정 스택, 단계별 룰 셋만 교체 | 원칙 5 |

해석이 실제 의도와 다르면 이 표를 고치고 본문을 따라 수정할 것.
